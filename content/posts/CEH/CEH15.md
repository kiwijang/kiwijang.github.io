## 前言

理解 SQL Injection 的成因、回應型態與參數化查詢，將資料和指令分開。

這篇依 EC-Council 教材 `module15.pdf` 整理，聚焦可確認的主要觀念，並非逐頁翻譯或完整操作手冊。各節頁碼指 **PDF 檔案內頁次**，包含封面及空白頁，不是書中印刷頁碼。實際測試以取得授權的範圍為前提。

## 1. 問題出在不可信資料改變查詢結構

SQL Injection 是外部輸入被不當組合進 SQL，使資料內容影響原本的查詢結構。影響可能包含資料讀取、修改或其他超出預期的操作。重點不是某個符號本身危險，而是系統是否把原本應作為資料的內容當成 SQL 指令解析。

*來源：本章 PDF 第 4–12 頁；以摘要及觀念解說重新整理。*

## 2. 有沒有顯示資料，不等於有沒有風險

教材區分 In-band、Inferential／Blind 與 Out-of-band 等型態，也介紹錯誤、查詢結果、真假條件與時間回應等線索。Blind 情境下不一定直接顯示資料，但行為差異仍可能透露資訊。因此隱藏錯誤頁不等於修好查詢組合問題。

*來源：本章 PDF 第 13–26 頁；以摘要及觀念解說重新整理。*

## 3. 從發現到確認，需要控制判斷範圍

本章介紹辨識輸入、判斷資料庫與弱點、分析影響及使用工具的流程。測試回應可能受快取、網路延遲或應用邏輯影響，不能僅憑一次錯誤或一次變慢就判定注入成立。本文保留方法論概念，不還原攻擊查詢與自動化利用。

*來源：本章 PDF 第 27–115 頁；以摘要及觀念解說重新整理。*

## 4. 參數化與最小權限處理不同層面

教材以型別明確的 SQL 參數示範資料與指令分離，也談資料庫帳號權限、錯誤處理與輸入檢查。參數化針對查詢組合方式；最小權限則降低出問題時可造成的影響。單純過濾幾個關鍵字，不能取代正確的查詢建構。

*來源：本章 PDF 第 132–146 頁；以摘要及觀念解說重新整理。*

## 5. 網路設備是補充，修正仍要回到應用

教材同時討論規避與防禦工具。辨識特定字串的規則可能受編碼或語法差異影響，因此防護不宜只依賴某種 Payload 是否被攔截。修復驗證應確認查詢處理方式已改善，並檢查相關輸入位置。

*來源：本章 PDF 第 116–131、147–152 頁；以摘要及觀念解說重新整理。*

## 重要名詞

| 名詞 | 這篇的理解重點 |
| --- | --- |
| SQL Injection | 不可信資料改變 SQL 查詢結構。 |
| Blind SQL Injection | 透過間接回應推論資訊的注入情境。 |
| Parameterized Query | 把查詢結構與參數資料分開處理。 |

## 理解用例（本文自擬）

查詢會員資料時，應讓會員編號作為參數值傳入，而不是將輸入字串直接接到 SQL 文字後面。這是查詢建構原則的說明，不是從教材截圖逐字還原的程式碼。
