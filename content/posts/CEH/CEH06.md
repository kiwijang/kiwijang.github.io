## 前言

以取得存取、權限提升、維持存取與隱藏痕跡四個階段，理解系統防護重點。

這篇依 EC-Council 教材 `module06.pdf` 整理，聚焦可確認的主要觀念，並非逐頁翻譯或完整操作手冊。各節頁碼指 **PDF 檔案內頁次**，包含封面及空白頁，不是書中印刷頁碼。實際測試以取得授權的範圍為前提。

## 1. 取得存取：密碼與驗證是第一道關卡

教材從 Windows 驗證、密碼雜湊與 Kerberos 等概念談起，再介紹各種密碼攻擊。線上猜測與離線處理取得的雜湊，是不同情境：限制登入次數能影響線上嘗試，卻不能直接阻止已外洩雜湊被離線分析。保護憑證資料與強化驗證需一起考慮。

*來源：本章 PDF 第 4–63 頁；以摘要及觀念解說重新整理。*

## 2. 利用弱點與提升權限要分開理解

取得一般帳號或服務存取，不代表已具有系統管理權限。教材將弱點利用與權限提升分開介紹，也涵蓋緩衝區溢位與多種系統弱點。分析事件時要確認最初入口、程式執行身分，以及權限如何改變，才能找到真正需要修復的位置。

*來源：本章 PDF 第 64–204 頁；以摘要及觀念解說重新整理。*

## 3. 維持存取可能藏在正常功能中

本章介紹遠端存取、鍵盤側錄、間諜程式、Rootkit、NTFS 替代資料串流、隱寫術，以及啟動與排程相關持續性機制。這些主題顯示，只清除一個可疑檔案不一定完成處置；仍需檢查啟動點、帳號、權限與其他被修改的設定。

*來源：本章 PDF 第 205–325 頁；以摘要及觀念解說重新整理。*

## 4. 隱藏痕跡讓證據保存更重要

教材最後討論停用稽核、清除紀錄、修改時間及其他反鑑識手段。從防禦角度看，重要紀錄不能只留在可能遭控制的主機上。事件分析也不宜只依賴單一檔案時間或單一紀錄來源。

*來源：本章 PDF 第 326–375 頁；以摘要及觀念解說重新整理。*

## 5. 依階段建立防護與查核問題

對應上述階段，可分別檢查驗證強度與憑證保護、修補及最小權限、持續性位置，以及稽核紀錄保存。這是本文依教材階段整理的閱讀方式，不代表每次入侵都按相同順序或經歷所有技術。

*來源：本章 PDF 第 57–63、198–204、323–325、374–375 頁；以摘要及觀念解說重新整理。*

## 重要名詞

| 名詞 | 這篇的理解重點 |
| --- | --- |
| Privilege Escalation | 從原有權限提升到更高權限。 |
| Persistence | 在重啟或其他變動後仍維持存取的能力。 |
| Anti-forensics | 干擾證據蒐集與事件追查的行為。 |

## 理解用例（本文自擬）

移除可疑程式後，如果惡意排程或被新增的高權限帳號仍存在，問題可能再度出現。處置紀錄應分別記下入口修補、權限復原、持續性清除與證據保存。

這個例子用於解釋觀念，不是教材案例、實測結果或作者經歷。

## 課堂照片補充：驗證、權限與可追查的操作

本節依 `4to6` 的 Q04、Q05、Q10–Q13、Q15、Q17 整理；[來源對照表](./CEH實作與資源.md)列出原檔。白板的驗證流程與實際執行畫面分開記錄，不能把概念圖當成已擷取憑證或提權成功。

### Kerberos、NTLM 與本機帳戶資料

Q04 將 DC、用戶端、伺服器、TGT 與服務票證畫在同一張圖。Kerberos 的學習重點是：取得 TGT 後，用它向 KDC 請求指定服務的票證，再向服務端出示服務票證；TGT 不等於通用的服務存取許可。這是流程摘要，不是完整封包交換。可參照 [Microsoft Kerberos 概觀](https://learn.microsoft.com/en-us/windows-server/security/kerberos/kerberos-authentication-overview)。

白板另一側的 SAM、密碼與 NTLM hash 應分開理解：SAM 涉及本機帳戶資料；網域帳戶與本機帳戶不是同一份資料。Hash 是雜湊，不能稱為可逆的編碼或加密。驗證套件與帳戶資料的關係可查 [Windows 驗證與認證處理](https://learn.microsoft.com/en-us/windows-server/security/windows-authentication/credentials-processes-in-windows-authentication)。

Q15 畫有 Windows 用戶端、Parrot／Responder、名稱解析與 challenge 的關係。**NTLM challenge-response 是根據認證資料與挑戰計算的回應，不等於明文密碼，也不能直接稱為 SAM 中的原始 NT hash。** 參照 [Microsoft NTLM 驗證說明](https://learn.microsoft.com/en-us/troubleshoot/windows-server/windows-security/ntlm-user-authentication)。照片沒有工具終端輸出、封包內容或擷取成功證據；名稱解析協定的部分手寫字不夠清楚，這裡不指定成某個已確認的協定，也不重建攔截命令。

Q15 還有 Account Lockout＝3 與重試次數的筆記；這只能當作課堂情境，不能推定所有本機與網域帳戶都採同一門檻或固定重試次數。實作應記錄目標帳戶所套用的實際政策與觀察事件，而不是嘗試把示範數字套到其他環境。

### 已有管理員身分，與取得管理員身分是兩件事

Q17 的視窗標題已顯示「系統管理員」。畫面執行新增 `user1` 本機帳戶、再加入本機 `administrators` 群組的命令，兩次都回報成功。這證明的是照片中的管理操作成功，**不是一般使用者越權成功**。命令沒有 `/domain`，也不能寫成新增網域管理員；文章不保留示範密碼。

若在自己的隔離實驗機重做帳戶管理，應另記錄操作前身分、變更前後的帳戶與群組成員、事件紀錄，以及移除測試帳戶的復原結果。本次只整理照片，沒有在這台電腦建立帳戶或修改群組。

Q10 的 `gpedit.msc` 路徑指向 Computer Configuration → Windows Settings → Security Settings → Local Policies → User Rights Assignment 的本機登入權限。登入權限與群組成員資格應分開核對；也不能假設每個 Windows 版本都有同樣管理介面。照片左側路徑引號示意不完整，沒有足夠服務設定能證明未加引號路徑弱點，因此不補利用步驟。

### Linux 命令：找出候選項目，不把清單當成漏洞

Q12 是教材命令說明頁，沒有實際輸出。下表保留可辨讀的命令，並補上其判讀邊界；不是已在本機執行的結果。

| 照片命令 | 可以觀察什麼 | 必須校正的解讀 |
| --- | --- | --- |
| `find / -perm -4000 -ls 2> /dev/null` | 尋找設有 SUID 位元的項目 | 沒有限定一般檔案、root 擁有者或可執行性；清單不是可利用弱點證明，錯誤輸出也被隱藏。 |
| `find / -name "*.txt" -ls 2> /dev/null` | 依名稱尋找 txt 項目 | 不等於已讀取內容；隱藏錯誤使結果可能不完整。 |
| `sudo -l` | 列出目前身分的 sudo 授權規則 | 可能要求驗證；有規則不表示可以不受限制地取得 root。 |
| `ps -ef` | 查看當下程序列表 | 程序快照不等於完整歷史。 |
| `mount` | 無參數時查看掛載資訊 | 不代表已執行新掛載。 |
| `route -n` | 查看數字形式的路由資訊 | 工具是否安裝與輸出內容取決於環境。 |
| `cat /etc/crontab` | 讀取系統 crontab 設定 | 不是列出正在執行的所有工作，也不涵蓋所有使用者排程及其他計時機制。 |
| `chmod o-w file` | 修改權限，移除 others 的寫入位元 | **會變更狀態**；不是取消所有人的寫入權，owner／group 仍需另外檢查。 |

`-perm` 的位元比對可查 [GNU Findutils 文件](https://www.gnu.org/software/findutils/manual/html_node/find_html/Mode-Bits.html)。進行自有主機稽核時，應保留權限、擁有者、檔案用途及必要的錯誤訊息，再判斷哪些設定需要改善；不要只憑 SUID 清單下結論。

### 日誌集中與時間線

Q05 畫出 Linux Syslog 從本機轉送到日誌伺服器，以及 Windows Event Viewer／Event Subscription。這說明日誌可集中蒐集，不表示所有 Linux 日誌都在 `/var/log/*.log`，也不表示開啟 Event Viewer 就會自動完成集中收集。

Windows 事件訂閱與收集的角色可參照 [Windows Event Collector](https://learn.microsoft.com/en-us/windows/win32/wec/windows-event-collector)。照片沒有提供收集端、傳輸保護或訂閱篩選的完整設定。延伸練習可以在自有實驗環境產生一筆可辨認的測試事件，核對本機與收集端的時間、來源主機與事件內容；尚未實際收到前，不填「轉送成功」。時間來源可對照 Module 04 的 Q09。

### OpenStego：驗證藏入與取出的資料一致

Q13 示意 Hide Data 的訊息檔、cover file、輸出圖片及密碼，再以 Extract Data 取回訊息。隱寫術處理資料藏在哪裡；加密處理資料可否被讀懂，兩者不能畫上等號。[OpenStego 官方頁](https://www.openstego.com/)與[命令列說明](https://www.openstego.com/cmdline.html)可核對功能及參數。

以下是依照片整理的**自有資料練習**，本次未安裝或執行：

1. 準備一份不含敏感資訊的文字檔與自己可使用的圖片，保留原檔。
2. 在 Hide Data 選擇訊息、cover、輸出位置及所需密碼設定；輸出另存，避免覆蓋原圖。
3. 使用 Extract Data 選取輸出檔，依設定提供密碼，解出到另一個資料夾。
4. 比較原始與取回檔案的內容或雜湊；一致才記錄還原成功，失敗則保存錯誤訊息與工具版本。

白板寫有 JPG 載體與 BMP 輸出，但不同版本／演算法支援的格式需以實際工具為準，不能直接保證照副檔名即可成功。照片沒有解出檔案或比較結果，所以不能記成已完成往返驗證。

Q11 的 Zero Trust 提醒可連回本節：身分、操作權限與證據需要持續核對；白板標語本身不是已部署零信任架構的證明。這批照片仍沒有完整的 Module 06 手冊實驗步驟。
