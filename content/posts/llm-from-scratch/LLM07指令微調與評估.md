## 會續寫，不一定會回答問題

預訓練模型看到「請摘要這段文字」，可能接著補出另一段要求，而不是交出摘要。指令微調透過示範，讓它學習要求與回答之間的關係。

本篇對應 Chapter 7。輸出頭維持詞彙表大小，訓練仍在預測下一個 token；真正改變的是資料格式、樣本內容，以及哪些位置參與 loss。

## 1. 把任務整理成一致的模板

一筆資料可以包含 instruction、可選的 input，以及示範 output。例如自行設計的資料：

```json
{
  "instruction": "把句子改寫得更簡潔。",
  "input": "由於今天正在下雨的緣故，所以活動取消。",
  "output": "因為今天下雨，活動取消。"
}
```

訓練前，要把欄位序列化成文字，例如：

```text
### Instruction:
把句子改寫得更簡潔。
### Input:
由於今天正在下雨的緣故，所以活動取消。
### Response:
因為今天下雨，活動取消。
```

這是本文的簡化示例，並非原章節完整模板。重要的是訓練與推論使用一致格式；沒有 input 時，也要定義清楚如何省略。欄位標題若只是一般字串，不會自動成為 tokenizer 的特殊 token。

## 2. 訓練有答案，推論停在回答開頭

訓練序列包含 prompt 與正確回答，讓模型在每個位置學習下一個 token。推論時則只給到回答起點，後面由模型生成。

這裡的差別很小卻很關鍵：若把測試題的正確回答一起送進去，再評估續寫，就不是在測模型能否自行回答那個問題。

切出生成回答時，最好依 prompt 的 token 長度切取新生成的 token，再解碼。用字元長度直接切文字，可能受到編碼與特殊 token 處理影響。

## 3. 每筆長度不同，如何組 batch？

同一個 batch 需要可堆疊的張量。動態 padding 會依該 batch 最長樣本補齊，而非每次都補到模型最大長度，有助於減少不必要計算。

輸入仍是 `[B, T]`，標籤仍向後移一格。不過補齊位置不應被當成大量重複答案來學習，所以需要區分：

| 機制 | 控制什麼 |
| --- | --- |
| Causal mask | 目前位置能否看見未來位置 |
| Padding／attention mask | 補齊位置是否參與注意力，視實作而定 |
| Loss 的 ignore_index | 哪些標籤不計入損失 |

三者不是同一件事。把標籤設為 `-100` 不會把輸入 embedding 也改成忽略，更不會自動產生 attention mask。

## 4. EOS 和 padding 共用 ID 時，要留一個結束訊號

原章節使用結束文字 token 進行補齊，並保留回答後第一個結束 token 作為訓練標籤，其餘多餘的補齊標籤改為 ignore index。這讓模型有機會學習「回答應該在這裡結束」。

下面是需安裝 PyTorch 的獨立補充範例，用玩具 ID 展示概念，不是完整 collate function：

```python
import torch

eos = 99
sequence = [10, 20, 30, eos]  # 內容加上結束 token
padded = sequence + [eos, eos]
inputs = torch.tensor(padded[:-1])
targets = torch.tensor(padded[1:])
# targets 的第一個 eos 在索引 2；索引 3 起為多餘補齊。
targets[len(sequence) - 1:] = -100
print(inputs.tolist())   # [10, 20, 30, 99, 99]
print(targets.tolist())  # [20, 30, 99, -100, -100]
```

不能把 `-100` 當作 token ID 丟進 embedding 查表；它是 loss 的忽略標記。實際資料若允許內容內出現特殊 token，還要仔細定義邊界，不能只搜尋 ID 就推斷回答結束。

## 5. 只忽略 padding，還是也忽略 prompt？

原章節主線忽略多餘 padding，prompt 區段仍參與語言模型 loss。另一種設計是把 prompt 對應的標籤也設為 `-100`，只學習回答區段。

```text
全序列目標：       prompt + response + EOS
只計回答區段目標： ignored  response + EOS
```

兩種方式都可用於指令微調，但不是同一個訓練目標。若自己改寫，必須依位移後的 targets 計算遮罩邊界，保留第一個回答 token 的監督，不要把它一起忽略。

資料截斷也要檢查：如果長 prompt 把回答全截掉，樣本可能不再提供預期的回答監督。應檢查有效回答 token 數，而不只確認張量長度沒超標。

## 6. 評估回答，不能只看一個總分

先建立獨立測試題，依任務檢查內容正確性、格式符合度、必要資訊是否完整，以及是否加入不存在的細節。對能明確比對的任務，優先使用可重複的規則或答案比對。

LLM-as-a-judge 可以協助比較開放回答，但評分也會受到裁判模型、提示與輸出順序影響。應保存裁判版本和評分規則，抽查高低分樣本，不能把分數直接當成人類品質的客觀真值。

比較微調前後時，要使用相同題目、模板與生成設定，並檢查訓練／測試間是否有近重複內容。Loss 下降和回答品質改善有關，但不能互相取代。

## 7. 完成主線後，接著學什麼？

指令微調是學習示範回答；偏好學習則引入「哪個回答較好」的訊號。DPO 等延伸方法，以及 LoRA 這類參數效率方法，各自解決不同問題。

練習時可以先固定一小組測試題，逐題保存微調前後回答與評語。若改成只計回答區段的 loss，就先確認標籤邊界，再比較品質，不要一次更換模板、模型和資料。

走到這裡，資料、模型、訓練和評估已經接成完整流程。下一次閱讀更大的 LLM 實作時，就能沿著同一條資料流，找出它在哪裡加入不同的設計。
